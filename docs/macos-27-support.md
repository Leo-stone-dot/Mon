# macOS 27 Support Guide

This guide covers support tasks for the macOS 27 Apple silicon release line.
For the release contract and approval gates, see
[macOS 27 Support Policy](macos-27-support-policy.md) and
[macOS 27 Validation Checklist](macos-27-validation-checklist.md).

## Supported installs

macOS 26+ releases support Apple silicon Macs only. New artifacts contain only
the `arm64` architecture and require macOS 26.0 or later. Intel Macs, Rosetta,
universal binaries, and macOS 25 or earlier remain on the final pre-migration
release.

## Evidence for bug reports

For macOS 26/27 issues, include:

- `sw_vers`
- Mac model and chip
- `uname -m`
- Amethyst version/build and install source
- Display topology from `system_profiler SPDisplaysDataType` when display or
  Space behavior is involved
- Separate Spaces, Stage Manager, full-screen Space, and Mission Control
  rearrange settings
- Accessibility, Screen Recording, Secure Input, and TCC reset state
- The exact command that failed
- `--debug-info` output

Release-candidate validation sessions should attach the directory generated by:

```bash
Scripts/capture-physical-validation-evidence.sh
```

The script intentionally fails on non-macOS-27.2 physical runners. Its output
is still useful as a collection bundle. macOS 27.2 physical validation is
currently deferred; if it is resumed, `physical-runner-preflight.txt` must
pass on a physical macOS 27.2 Apple silicon Mac before claiming that evidence.

## Accessibility and TCC reset

Amethyst requires Accessibility permission. On macOS 27, confirm the exact
permission state in System Settings before reporting a window-management
failure.

To reset Accessibility state for a clean validation run:

```bash
tccutil reset Accessibility com.totoleo.Amethyst
```

After resetting, quit and relaunch Amethyst, grant Accessibility again, and
record whether the issue reproduces before and after the grant. Screen
Recording is not expected to be required for normal Amethyst window management;
if macOS prompts for it, include that prompt in the report.

### Local Accessibility testing with development builds

Ad-hoc signed Debug builds change their code signature on every rebuild, so the
Accessibility grant is invalidated each time. For local runtime testing, build
through the development script, which signs with a stable identity and relaunches:

```bash
Scripts/dev-build.sh --run
```

The first run creates the `Amethyst Dev` identity. Then add
`build/DerivedData/Build/Products/Debug/Amethyst.app` to
System Settings → Privacy & Security → Accessibility. Because the identity is
stable, later rebuilds keep the same grant after `Scripts/sign-dev-app.sh` runs.

Do not run a raw `xcodebuild test` in the same desktop session when Accessibility
is granted to the development app: Xcode can launch an unsigned test host whose
identity changes per build. For a local runtime test, use:

```bash
Scripts/dev-test.sh
```

It builds tests without launching them, signs the Debug test host with
`Amethyst Dev`, then uses `test-without-building`. The normal CI script remains
for a dedicated self-hosted runner carrying the `ci` label, not a daily-use Mac.

## Space command degradation

Space-dependent commands may be disabled when private Space APIs or event
posting are unavailable. Core tiling, focus, and screen movement should
continue.

When Space discovery is unavailable, Amethyst selects visible active windows
on the current display without applying a Space-ID filter. It retains the
currently selected layout until Space discovery recovers. Once it can identify
the current desktop again, it resumes the layout stored for that desktop.

On macOS 26, private CGS reports user desktop Spaces with type `4`; older
releases used type `0`. Amethyst treats type `4` and legacy type `0` with a
non-empty UUID as user Spaces. If a layout selection does not restore after an
OS update, check `--debug-info` for the reported Space types and contract
result; normal tiling should still remain available during this degradation.

Logs may include reasons such as:

- `Space information is unavailable`
- `Current Space is not listed in the available Spaces`
- `Target Space index is out of range`
- `No focused window is available`
- `Focused window has no screen`
- `No user Space exists in the requested direction`
- `secureInputEnabled`
- `eventCreationFailed`
- `missingDragPoint`

When reporting Space command failures, include whether Secure Input was active
or suspected. Secure Input causes throw-to-Space to fail closed before any drag
events are posted. When it is active, the status menu displays **Secure Input
is enabled; throw-to-Space is unavailable**; ordinary tiling, focus, and
screen movement remain available.

## Layout state recovery

If the status menu displays **Saved layout state could not be restored; using
default layouts**, Amethyst encountered an invalid or newer saved layout state
and started with the configured default layouts. It leaves the original state
and one backup in UserDefaults for diagnosis; it does not remove YAML, JSON,
custom layout files, shortcuts, floating rules, or margins.

After recording the message and `--debug-info` output for a report, choose
**Reset Layouts** from the status menu to remove the saved layout state and its
backup. The next launch will create state from the current configuration.

## Per-display and per-Space tiling

The selected layout is saved independently for each display × Space target.
Open **Layouts** after focusing a window on the intended display; the first
disabled menu item identifies that display and Space. Layout selections are
saved immediately.

To disable tiling only for the target display and Space, choose **Disable
Tiling for This Display & Space**. Other displays and Spaces continue using
their own tiling settings; choose **Enable Tiling for This Display & Space**
to restore this target. This differs from global **Disable Tiling**, which
affects all windows.

## Start at Login

macOS 27 builds use `SMAppService.mainApp`. Legacy login item state is not
migrated. If Amethyst does not start at login:

1. Open the Amethyst status menu.
2. Toggle **Start Amethyst on Login**.
3. If the menu says approval is required, open System Settings and approve
   Amethyst in Login Items.
4. Record the menu state and System Settings state in the issue.

## Rollback

macOS 26+ artifacts must not be offered to Intel Macs or macOS 25 and earlier.
Older systems should remain on the final pre-migration Intel-compatible
release from the GitHub releases page.

To roll back on a supported macOS 26+ Apple silicon Mac:

1. Quit Amethyst.
2. Download the previous notarized Amethyst artifact from the releases page.
3. Replace the application bundle.
4. Launch Amethyst and re-check Accessibility and Login Items state.
5. Attach the version/build before and after rollback.

Do not run macOS 26-only setup steps on macOS 25 or earlier machines.
